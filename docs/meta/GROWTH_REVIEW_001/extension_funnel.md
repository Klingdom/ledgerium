# GROWTH_REVIEW_001 -- Chrome Web Store Funnel Assessment (Acquisition + Activation)

**Agent:** chrome-web-store-expert
**Date:** 2026-09-02
**Scope:** Chrome Web Store listing and extension install funnel as an acquisition/activation channel for Ledgerium AI.
**Constraint honored:** no edits proposed or made to apps/extension-app/manifest.json permissions, content_scripts, or the capture pipeline. Analysis and listing/copy recommendations only.

**Headline finding, before anything else:** Chrome Web Store search is not currently a channel at all -- the extension has never been published. EXTENSION_CONFIG.chromeStoreUrl in apps/web-app/src/lib/config.ts (line 16) is still the literal string 'https://chrome.google.com/webstore/detail/ledgerium-ai/placeholder', and apps/web-app/src/lib/install.ts (isChromeStorePublished, lines 44-48) gates the entire site's install UX on that placeholder marker. Every install button on the site (apps/web-app/src/components/ExtensionInstallButton.tsx) currently renders the direct-download/sideload path, not a Chrome Web Store link. This one fact reframes every question below: the near-term opportunity is not "improve our Chrome Web Store ranking," it is "ship what already exists in the repo to actually get a listing."

---

## 1. Is Chrome Web Store search a viable acquisition channel?

**Yes -- conditionally, and it is currently the better bet of the two channels available.** Reasoning:

- **Traffic reality forces the question.** 25 search clicks in 3 months on the whole site is not a channel, it's noise. Google organic requires domain authority Ledgerium does not have and will not have soon (the site is roughly 4 months old by its own SEO/AEO program dates in CHANGELOG.md). The Chrome Web Store has its own internal search engine, its own ranking signals (title/description keyword match, install velocity, rating, recency of updates), and zero dependency on backlinks or domain authority. A brand-new listing with zero external traffic can still surface for a query if the title/description match well and the category is right -- that is structurally different from Google, where a 4-month-old unlinked domain is nearly invisible regardless of on-page quality.
- **Competitive density is real but not saturating.** docs/meta/CHROME_EXTENSION_STORE_REVIEW_001.md (section 8, competitive-researcher) and the homepage/comparison page apps/web-app/src/app/(public)/compare/scribe/page.tsx both establish Scribe, Tango, Loom, and UI.Vision as the direct competitive set. These are real, well-funded competitors with existing Chrome Web Store listings and presumably thousands of reviews -- Ledgerium will not outrank "Scribe" on the branded term "scribe," and does not need to. The category query space ("SOP generator," "process documentation," "screen recorder for documentation," "workflow recorder," "standard operating procedure tool") is not a winner-take-all query the way "screen recorder" (generic, huge volume) is -- it is a long-tail, intent-qualified space where a handful of listings compete, and a well-titled new entrant can realistically appear on page 1 or 2 for the specific SOP/process-documentation phrasing (see section 2 -- this phrasing is currently absent from the extension's own listing copy, which is the single biggest lever available).
- **Intent match is excellent.** Someone typing "SOP" or "process documentation" or "workflow recorder" into the Chrome Web Store search bar is, by definition, already extension-shopping with high purchase/install intent -- a much higher-intent audience than a cold Google searcher landing on the marketing site. This is the core argument for prioritizing CWS discoverability over incremental SEO work: every install-intent visitor who finds Ledgerium via CWS search skips the entire top-of-funnel (they never need to find ledgerium.ai first).
- **But it only works once listed, and cold-start review/rating scarcity is a real early handicap** (see section 4). A brand-new listing with 0 ratings will rank below a competitor with a large rating and review count for the same query even with better keyword match -- Chrome Web Store's ranking algorithm weights install count and rating heavily once results are keyword-tied. The honest framing: CWS search is viable as a discovery-and-conversion channel for a cold-start product, better than Google SEO in the first 6-12 months because it does not depend on domain authority, but it is not going to produce meaningful volume until (a) the listing exists, (b) the listing copy targets the right queries, and (c) enough installs/ratings accumulate to clear the cold-start ranking floor. It should be pursued in parallel with, not instead of, the SEO/AEO content engine already built (apps/web-app/src/content/).

**Verdict: pursue it, but the first and only truly load-bearing action is publishing a real listing.** Every recommendation below is secondary to that.

## 2. Listing improvements, ranked by expected effect on installs

### P0 -- will suppress installs or block ranking entirely if not fixed

**2.1 Publish the extension -- nothing below matters until this happens.**
apps/web-app/src/lib/config.ts line 16 (chromeStoreUrl: '.../placeholder'). Per docs/runbooks/CHROME_STORE_SUBMISSION.md and the two prior policy audits (docs/meta/CHROME_STORE_REVIEW_002.md, docs/meta/CHROME_EXTENSION_STORE_REVIEW_001.md), the codebase has already done most of the policy-cleanup work needed for submission: src/viewer/ and src/background/telemetry.ts are removed, the tabs/activeTab permissions are gone from manifest.json, the API key was migrated to chrome.storage.local (confirmed in apps/extension-app/src/sidepanel/screens/ProcessScreen.tsx lines 195-222, comment cites "CHROME-002 fix"), and HTML output is now escaped (ProcessScreen.tsx lines 181-188, escapeHtml). What remains open per those two audits and still verified present in the current tree:
  - apps/extension-app/src/sidepanel/components/SidebarProcessMap.tsx + SidebarStepDrawer.tsx and apps/extension-app/src/background/workflow-report-builder.ts are still shipped, still wired into ProcessScreen.tsx (Map tab, SOP tab, "Download Workflow Report" button at ProcessScreen.tsx lines 596-612), and @xyflow/react (roughly 800KB) is still a dependency (apps/extension-app/package.json line 22). Both audits flag this as the number-one single-purpose review-friction item (downstream interpretation of the JSON, not creation of it) -- this is a policy/engineering decision for the change-control owner, not something I'm proposing to edit, but it is the reason the CHROME_STORE_REVIEW_002 verdict tops out at "MAJOR-CLEANUP REQUIRED" rather than "READY."
  - apps/extension-app/icons/icon-128.png is declared as the 128x128 icon in manifest.json (lines 24, 33) but is actually 1024x1024 pixels, 910,663 bytes (verified directly by reading its PNG IHDR chunk, not assumed). Every other icon (16/32/48) is correctly sized (verified the same way: 16x16/214B, 32x32/596B, 48x48/1106B). This is a submission-readiness defect the runbook's own validation step recorded without flagging (docs/runbooks/CHROME_STORE_SUBMISSION.md around lines 65-66 literally logs "icon-128.png (910.66kB)" next to three sub-2KB siblings and moves on). A 128px icon at 900KB either fails Chrome's store-icon upload validation outright or ships a bloated, wrong-dimension asset into the package -- either way this is a listing-quality defect that will surface the moment someone tries to complete the Dashboard's separate "Store icon" upload field, which requires an exact 128x128 image.
  - This is squarely inside my mandate as fit-for-purpose analysis (not a code edit) because it is the reason the listing cannot go live as-is.

**2.2 Rewrite the name, summary, and description to target what people actually search, not what the extension mechanically does.**
Current listing copy (apps/extension-app/manifest.json lines 3-5, and the submission-form fields drafted in docs/runbooks/CHROME_STORE_SUBMISSION.md around lines 333-335):
- Name: "Ledgerium AI Recorder"
- Description: "Record browser workflows (clicks, navigation, form labels) and export them as JSON. Optional upload to your Ledgerium workspace."
- Draft Store Summary (max 132 chars): "Record browser workflows and export them as JSON. Optional upload to your Ledgerium workspace."

This copy describes the mechanism (clicks, navigation, JSON export) and is silent on the outcome a searcher is looking for. Compare to the web app's own marketing copy, which already knows the right vocabulary -- apps/web-app/src/app/(public)/product/page.tsx line 25 titles itself "Browser Workflow Recorder & SOP Generator -- Ledgerium AI" and the homepage headline is "Your SOP says 5 steps. Your team takes 17." (apps/web-app/src/app/(public)/page.tsx lines 86-88). None of that vocabulary -- "SOP," "standard operating procedure," "process documentation," "workflow documentation" -- appears anywhere in the extension's own Chrome Web Store name, description, or summary. Chrome Web Store search ranks primarily on title and description keyword match; an extension named "Ledgerium AI Recorder" with a description about "clicks, navigation, form labels, JSON" will not surface for "SOP," "process documentation," or "workflow documentation generator" queries even though the product is squarely built for that job (packages/process-engine literally builds SOPs -- see SOPStep/SOPView in ProcessScreen.tsx lines 49-90).

Recommended direction (copy only -- for the CEO/marketing owner to approve and enter on the submission form, not something I am changing):
- Name candidate: "Ledgerium -- SOP & Process Documentation Recorder" or "Ledgerium AI -- Workflow Recorder & SOP Generator" (keep "Ledgerium" for brand continuity with the web app; add the job-to-be-done term that is currently missing entirely).
- Summary candidate (max 132 chars): "Record any browser workflow. Get an instant SOP, process map, and AI-readiness report -- no writing, no screenshots."
- Description candidate: lead with the outcome (SOP + process map generated automatically from a recording), then the mechanism (clicks/navigation/form labels, on-device processing, optional sync), matching the single-purpose statement already drafted in docs/meta/CHROME_EXTENSION_STORE_REVIEW_001.md section 7 and docs/meta/CHROME_STORE_REVIEW_002.md section 7, both of which already correctly foreground "structured process map, SOP, and exportable JSON" -- that language should be promoted into the name and summary, not left only in the long description, since CWS search weights title/short-description far more than body copy.
- This is the single highest-leverage, lowest-risk lever in this entire assessment: it is pure copy, touches no manifest permission or capture code, and directly targets the CWS search relevance signal for the exact terms a category-shopping user would type.

**2.3 Category selection.**
docs/runbooks/CHROME_STORE_SUBMISSION.md line 336 specifies Category: Productivity. That is defensible (Scribe and Tango also list under Productivity/Workflow & Planning) but should be confirmed against Chrome Web Store's current category taxonomy at submission time -- "Productivity" is broad and puts Ledgerium in direct competition with every to-do app and note-taking extension. If Chrome Web Store's taxonomy has surfaced a narrower "Workflow & Planning" or similarly adjacent sub-bucket by submission time, that narrower bucket will have less noise and a better intent match. Low effort, worth a 5-minute check at submission time; not independently blocking.

### P1 -- meaningfully improves install conversion once listed

**2.4 Screenshots exist but are not composed for a store listing -- and there are two competing sets.**
Two separate screenshot sets exist in the repo: docs/store-assets/chrome/ (4 files, verified 1280x800 via docs/runbooks/CHROME_STORE_SUBMISSION.md BLOCKER-8, real captures of the actual sidepanel next to a real fixture page) and docs/chrome-store-assets/extension/ (7 raw sidepanel-only screenshots plus 7 "store-XX-..." composited files that the runbook itself calls out as not real -- "the pre-existing scripts/capture-sidepanel-screenshots.ts composites a static HTML sample into a hand-built fake browser chrome with invented marketing copy and a fabricated address bar... none of its output pixels come from the running extension" and additionally ships at 2560x1600, the wrong dimension for Chrome's 1280x800 requirement). Two risks here: (a) if whoever completes the submission form grabs images from docs/chrome-store-assets/extension/store-*.png instead of docs/store-assets/chrome/, the listing ships fabricated screenshots with invented copy that never ran in the real product -- a direct Chrome Web Store policy risk (misleading listing content) independent of the technical wrong-dimension defect; (b) the correct, real, 1280x800 set at docs/store-assets/chrome/ only has 4 images and none of them show the SOP tab or the process map tab -- the two artifacts most differentiated from a generic "click recorder." Recommend regenerating with apps/extension-app/scripts/capture-chrome-store-screenshots.ts (per its own regeneration instructions in the runbook) to add a 5th real screenshot of the SOP/Map view, and clearly retiring or relabeling docs/chrome-store-assets/extension/store-*.png so nobody uploads the fabricated set.

**2.5 First screenshot / listing icon should show the outcome, not the empty state.**
Given CWS search results display the icon and first screenshot thumbnail prominently, and the current first real screenshot is 01-idle.png (an empty sidepanel with a text field), consider whether the SOP or process-map screenshot should be promoted to first position once captured -- an empty form field does not visually communicate "this generates SOPs," while a populated SOP view does. This is a sequencing/compositing decision for whoever runs the capture script, not a code change.

**2.6 No reviews/ratings exist yet -- expected and unavoidable, but plan for it.**
Chrome Web Store ranks partly on install velocity and rating; a 0-review, 0-install listing will not out-rank Scribe/Tango on shared terms on day one regardless of copy quality. This is not fixable pre-launch, but it argues for (a) submitting with "Unlisted" visibility first exactly as the runbook already plans (docs/runbooks/CHROME_STORE_SUBMISSION.md line 341), (b) seeding the first handful of installs/ratings from the existing (tiny) direct-download user base or a private beta list before flipping to Public, so the listing does not launch into public search with a literal zero-social-proof state, and (c) once live, actively prompting satisfied users for a rating from within the product (no such prompt currently exists anywhere in the extension or web app that I found).

### P2 -- polish, will not independently move install numbers

**2.7 docs/chrome-store-assets/ vs docs/store-assets/ naming collision** is confusing repo hygiene (two near-identically-named directories serving the same purpose, one containing fabricated assets) -- worth consolidating when someone next touches this area, not urgent.

## 3. Friction in install -> first-recording

This is the step-by-step path a new user actually walks, with the friction point at each hop.

1. **Discovery -> install page.** apps/web-app/src/app/(public)/install/page.tsx and install-extension/page.tsx both exist and both route through ExtensionInstallButton (apps/web-app/src/components/ExtensionInstallButton.tsx), which resolves to the direct-download .zip today (resolveInstallTarget in apps/web-app/src/lib/install.ts lines 57-76) because the store URL is still a placeholder. This is the single biggest friction point in the whole funnel, and it is entirely a consequence of sections 1 and 2.1: instead of one click ("Add to Chrome"), the current path is: download a .zip, extract it, navigate to chrome://extensions, toggle on Developer Mode, click "Load unpacked," pick the extracted folder, find the extension in the puzzle-piece menu, pin it. apps/web-app/src/app/(public)/install/page.tsx lines 76-273 documents this full 4-step sideload flow in detail (with a ServiceOfferCard "Guided Onboarding" white-glove upsell placed directly after it -- install/page.tsx lines 292-308 -- an implicit admission by the product itself that this flow is hard enough to warrant a paid human-assisted option). For a business user evaluating a documentation tool, "enable Developer Mode and load an unpacked extension" is a materially higher-trust ask than "Add to Chrome," and is the kind of step that visibly triggers Chrome's own warning banner about developer-mode extensions -- which the FAQ on the same page has to explicitly pre-empt ("Chrome is showing a warning about Developer mode extensions... This is expected behavior... the extension is safe to use," install/page.tsx lines 457-460). Every install that survives this path is a user who pushed through real, self-inflicted friction; every drop here (the overwhelming majority, per standard sideload-vs-store conversion benchmarks) is silently lost with zero signal, because installClickEvent in apps/web-app/src/lib/install.ts lines 82-87 only fires on the initial button click, not on completion of the sideload steps -- there is no way to tell how many of the 25 site visitors who clicked "install" ever actually finished loading the unpacked extension.

2. **First launch -- the extension icon to sidepanel.** Once loaded, the user clicks the toolbar icon (action.default_title: "Open Ledgerium Recorder", manifest.json line 31) and lands on apps/extension-app/src/sidepanel/screens/IdleScreen.tsx. This screen has zero onboarding content. It is a text input ("What are you recording?", placeholder "e.g. Submit expense report"), a "Start Recording" button, a collapsed "Sync Settings" accordion, and -- if no prior recordings exist -- the string "No recordings yet / Completed sessions will appear here" (IdleScreen.tsx lines 248-253). There is no explanation of what the extension does, no hint that recording works fully standalone without an account, no link back to the web app, and no indication of what happens after you click Start. Two prior audits both independently flagged this exact gap and it remains unaddressed: docs/meta/CHROME_STORE_REVIEW_001.md section 9 (D-UX-EXT-2, "One-screen contextual hint on idle empty state," and QA checklist item SHOULD-6, "Empty-state copy on IdleScreen explaining first-recording") and docs/meta/CHROME_EXTENSION_STORE_REVIEW_001.md section 3 (P1-6, "No in-extension data-use disclosure... Chrome user-data policy expects a disclosure within the extension surface, not just a URL"). Both remain open in the code today.

3. **Recording start -> "Arming."** apps/extension-app/src/sidepanel/screens/ArmingScreen.tsx is a clean, minimal spinner ("Starting session... Preparing to capture your workflow") -- no friction here, this screen is fine.

4. **Mid-recording.** Not reviewed in depth here (out of scope per the capture-pipeline change-control constraint), but worth noting for activation: nothing on IdleScreen tells the user in advance what a "step" looks like or how long to record before stopping produces a meaningful SOP -- first-time users have no calibration for "have I recorded enough."

5. **Stop -> review (ProcessScreen.tsx).** This is actually the strongest part of the funnel: the user immediately sees a populated Map/SOP/Export view with real derived output (ProcessScreen.tsx lines 758-885), which is the moment the product's core value (automatic SOP generation) becomes visible. The primary CTA here, "Open in Ledgerium AI Website" (ProcessScreen.tsx lines 576-593), is well-placed as the bridge back to the web app for anyone who wants persistence -- but it silently falls back to opening /upload with no explanation if no Sync URL/API key is configured (ProcessScreen.tsx lines 482-487, openInWebsite), i.e., a first-time user who never touched the collapsed "Sync Settings" accordion on IdleScreen clicks "Open in Ledgerium AI Website" expecting their recording to appear there, and instead gets bounced to a generic /upload page with no context carried over about what just happened or why. This is an activation-path defect: the extension's whole reason for existing is to feed the web app, and the connective step between "I just recorded something" and "it's now visible in my Ledgerium account" is not a one-click default -- it requires the user to have pre-configured a Sync URL and API key from the web app's account settings before recording, which nothing on IdleScreen prompts them to do.

6. **Minor, compounding UX friction (not blocking, but each one is a small tax on a first-time user's confidence):**
   - IdleScreen.tsx line 163 still uses a native window.confirm() dialog for deleting a recording ("Delete X? This cannot be undone.") -- flagged for replacement in both prior audits (CHROME_STORE_REVIEW_001.md CLEANUP-10, CHROME_STORE_REVIEW_002.md P2-E) and still present; native browser confirm dialogs read as unpolished inside an otherwise custom-styled panel.
   - ErrorScreen.tsx line 16 renders a generic "Something went wrong" for every error path, with only a raw, unmapped error string beneath it (SHOULD-7 in CHROME_STORE_REVIEW_001.md section 7, still open) -- a first-run user who hits any error gets no actionable next step.
   - Both /install and /install-extension exist as separate, largely-overlapping public pages with slightly different copy and CTA labels ("Download Chrome Extension" vs "Install Chrome Extension") -- this is a minor site-structure inconsistency, not user-facing friction per se, but it means analytics/SEO effort is split across two pages instead of consolidated on one canonical install destination.

**Net assessment:** the install-to-first-recording path is workable for a technically confident user who trusts the brand enough to push through Developer Mode, but it is not a path a cautious business evaluator finishes on the first try, and the one moment that should feel like magic -- stopping a recording and getting an instant SOP -- is undercut by a silent, unexplained fallback when sync isn't pre-configured. Fixing item 2.1 (publish to the store) removes the largest single friction point in the entire funnel without touching a line of capture code.

## 4. Policy or trust risk that would suppress installs

1. **Single-purpose ambiguity is still open, per the codebase's own two most recent policy audits.** SidebarProcessMap.tsx/SidebarStepDrawer.tsx (React Flow visualization, @xyflow/react dependency) and workflow-report-builder.ts (in-extension HTML report generation, still wired to a "Download Workflow Report" button in ProcessScreen.tsx lines 596-612) remain shipped even though both docs/meta/CHROME_STORE_REVIEW_002.md (sections 1 and 8) and docs/meta/CHROME_EXTENSION_STORE_REVIEW_001.md (sections 3 and 9) independently flag them as downstream interpretation of the recorded JSON rather than creation of it -- the textbook shape of a single-purpose soft-reject ("why does a workflow recorder also render flowcharts and PDF-style reports in-extension?"). This is not something to remediate via this analysis (it is exactly the kind of capture/manifest-adjacent surface under change control), but it is the top-ranked reason docs/meta/CHROME_STORE_REVIEW_002.md caps first-pass approval probability at 60-70% even after the already-completed cleanup, versus 85-92% if the remaining removal is completed. A soft-reject cycle adds 7-28 days per CHROME_STORE_REVIEW_002.md's own scenario table -- every day the listing isn't live is a day the extension isn't discoverable in CWS search at all, so this indirectly suppresses installs by delaying launch.

2. **host_permissions ["<all_urls>"] plus declarative content_scripts matching <all_urls>** is the single highest-scrutiny signal a Chrome reviewer (and a cautious enterprise IT buyer independently vetting the extension before a team rollout) will see first. Both audits agree this scope is defensible and necessary for the stated recording use case (a recorder cannot pre-declare which internal tools a user will record on) and is standard for this category (Scribe/Tango/Loom carry the same scope) -- but it is only defensible, not invisible, and it is exactly the kind of permission line that makes a security-conscious buyer pause during evaluation. The mitigation is not a manifest change; it is what the listing itself says about it. The current draft justification text in docs/runbooks/CHROME_STORE_SUBMISSION.md lines 281-288 is good and should be surfaced not just in the developer-dashboard justification field (which end users never see) but prominently in the public-facing store description and on apps/web-app/src/app/(public)/install/page.tsx, which already does a reasonable job of this today (the "Captured / Not captured" comparison at install/page.tsx lines 350-404) -- that framing should be echoed into the Chrome Web Store long description itself once published, since that page's trust framing does not currently exist anywhere in the store listing copy.

3. **Zero reviews/ratings at launch** (covered in section 2.6) is a trust signal a cautious business user actively checks -- a 0-review productivity extension requesting broad host access is a harder sell than the same extension with even a handful of ratings. Plan a seeded-install strategy for the first weeks post-launch rather than relying on cold organic search traffic to self-generate the first reviews.

4. **Privacy policy quality is actually a strength, not a risk** -- worth noting explicitly since it's the one trust dimension that's in good shape. apps/web-app/src/app/(public)/privacy/extension/page.tsx is a dedicated, extension-specific policy (not a generic reused page), effective-dated June 18 2026, opens with an explicit "Trust Commitments" list (user-initiated only, no background monitoring, no screenshots, no keystroke logging, incognito inaccessible -- lines 53-60), and the drafted Chrome Web Store Data Safety disclosure table in docs/runbooks/CHROME_STORE_SUBMISSION.md lines 308-322 is specific and accurate (masks passwords/credit cards/SSN at capture, discloses upload is opt-in and user-endpoint-only, explicitly states no data sale and zero third-party analytics SDKs in the bundle -- independently verified true by the CHROME_EXTENSION_STORE_REVIEW_001 security pass). This is a genuine differentiator against a competitor like Tango, which per CHROME_EXTENSION_STORE_REVIEW_001.md section 8 discloses a broader 6-category data footprint versus Ledgerium's narrow 2-category disclosure -- this should be marketed as a positioning asset in the store listing description itself ("narrower data footprint than comparable tools"), not just buried in a permission-justification field.

## Bottom line

The Chrome Web Store is a genuinely better near-term acquisition bet than Google search for a zero-authority, zero-revenue site -- but that thesis is entirely theoretical today because EXTENSION_CONFIG.chromeStoreUrl (apps/web-app/src/lib/config.ts line 16) is still a placeholder and nothing has been submitted. The engineering path to submission is short (the codebase has already done the hard parts -- API key migration, XSS fix, dead-code removal, permission trimming); what remains is a product/policy decision on the sidebar map and workflow-report surfaces, a fixed 128x128 icon file, and, the highest-leverage item in this whole review, rewriting the listing name/summary/description to say "SOP" and "process documentation" instead of only "clicks, navigation, JSON," since that vocabulary gap is the difference between showing up in Chrome Web Store search for the exact queries a prospective customer would type and not showing up at all.
